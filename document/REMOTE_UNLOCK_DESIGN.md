最終更新: 2026-10-07　状態: **フェーズ 1〜3 のコードを実装済み（シミュレーション検証済み、実機では未有効化）**。BLE コマンドの実機検証は完了（§0）。進捗は §14。前提となる状態通知ブリッジは `MQTT_BRIDGE_DESIGN.md` を参照。

## 0. 実機検証の結果（2026-10-07）

`pi/sesame_cmd.py`（検証用 CLI）で Sesame 5 B に対して実施。

| 操作 | 応答 | 状態変化 | 所要時間 |
|---|---|---|---|
| lock（施錠済みに施錠） | res=0 成功 | LOCKED のまま | 0.09 秒 |
| unlock | res=0 成功 | LOCKED → UNLOCKED（位置 -98°） | 1.27 秒 |
| lock（4 秒後の再施錠） | res=0 成功 | UNLOCKED → LOCKED（位置 0°） | 1.21 秒 |

- 送信形式: `05 ‖ AES-CCM( item(82|83) ‖ 履歴タグ )`、履歴タグは「長さ 1B + UTF-8（最大 20B）」。公式 SDK の最新版は 2B の種別プレフィックス形式だが、長さプレフィックス形式でも受理される。
- 応答は `07 ‖ item ‖ res`（res 0 = 成功）が即時に返り、続いて mechStatus が動作中→確定の順で 1〜2 回届く。**完了判定は応答ではなく mechStatus の確定状態で行う**（応答 res=0 の直後はまだ UNLOCKED のことがある）。
- **制約: Pi の Bluetooth アダプタは 1 つで、同じ錠への接続は 1 本しか持てない。** ブリッジが接続を保持している間、別プロセスから接続すると初期乱数が再送されずログインできない。したがって遠隔操作の実装は**ブリッジ本体が自分の BLE セッションでコマンドを送る**形にする（検証 CLI はブリッジ停止中のみ使う）。


## 1. 目的と範囲

- スマホアプリから MQTT を通じて、Pi に接続された Sesame 5 を施錠・解錠できるようにする。
- **誰が・どの錠を・いつ**操作できるかを厳密に制御し、ブローカーが第三者（クラウド）であることを前提に安全性を保つ。
- 対象は `config.json` の `devices[]` にある錠（現在は「Sesame 5 T」「Sesame 5 B」）。Touch Pro は対象外。

やらないこと: トグル操作（現在状態に依存して意味が変わり、誤操作の原因になる）、Sesame 本体の設定変更、鍵（secret）の配布。

## 2. 脅威モデル

| 脅威 | 想定 | 対策（章） |
|---|---|---|
| ブローカーの盗聴・なりすまし | 公開ブローカー、またはクラウド事業者の侵害。トピックと内容が読まれ、任意のメッセージを注入される | 署名付きコマンド、ブローカーを信頼しない設計（§4） |
| 再送攻撃 | 正規の解錠メッセージを記録して後で再送 | タイムスタンプ窓 + nonce（§5.3） |
| 権限外操作 | 家族 A が許可されていない錠を開ける、ゲストが期限後に開ける | 権限表を Pi 側で検証（§4） |
| スマホ紛失・退去 | 端末ごと鍵が盗まれる、ユーザーを失効させたい | ユーザー単位の鍵と即時失効（§4.3） |
| 連打・自動化による乱用 | 誤動作や総当たり | レート制限（§6） |
| Pi 侵害 | Pi が乗っ取られれば Sesame の secret ごと奪われる | 本書の範囲外。Pi の OS 側対策（ssh 鍵認証、更新）に委ねる |

**基本方針: ブローカーは「配達人」としてしか信頼しない。認可の判断と検証はすべて Pi 上のブリッジで行う。**

## 3. 権限モデルの選択肢（「誰がどの錠を開けられるか」）

### 案 A: ブローカーの ACL だけで制御

ユーザーごとに MQTT 認証情報を発行し、ブローカーの ACL で「`<p>/sesame5_t/cmd` へ publish できるのは alice と bob」のように制御する。

- 長所: 実装が最小。ブリッジは届いたコマンドを実行するだけ。
- 短所: 安全性がブローカー任せ。ブローカーの設定ミス・漏洩・事業者側の問題で解錠されうる。再送攻撃を防げない。期限付き・時間帯付きの権限を表現しにくい。無料枠では ACL の粒度が限られる。
- 評価: **単独では不採用**。多層防御の外側として併用する（§7）。

### 案 B: Pi 側の権限表 + ユーザー署名（推奨）

各ユーザーが自分の鍵ペアを持ち、コマンドに署名する。Pi は「ユーザーの公開鍵」と「ユーザーの権限表」を持ち、署名・権限・時刻・nonce を検証してから BLE コマンドを送る。

- 長所: ブローカーに依存しない。粒度（錠 × 操作 × 期間 × 時間帯）を自由に設計できる。失効は Pi 側のファイルから 1 行消すだけで即時。再送攻撃を防げる。
- 短所: ユーザー鍵の配布（§4.4）と Pi 上の権限表の管理が必要。
- 評価: **採用**。

### 案 C: 発行者が署名したケイパビリティトークン

管理者の鍵でユーザーごとの「許可証」（錠・操作・期限を含む）に署名して配り、Pi は管理者の公開鍵で許可証を検証する。Pi に事前登録なしで新しいゲストを増やせる。

- 長所: Pi を触らずにゲスト発行できる。期限で自動失効。
- 短所: 期限前の即時失効には失効リスト（結局 Pi の更新）が必要。複雑。
- 評価: 将来、ゲスト運用が増えたら案 B の上に追加する。初版では採らない。

### 参考: Sesame 公式の権限モデル

CandyHouse 公式アプリも同じ問題を「ユーザーごとの鍵（オーナー / マネージャー / ゲスト）+ 期限付きゲスト鍵 + QR で配布 + クラウドで管理」で解いている。本設計の案 B はこれを自前の MQTT 経路に写したもので、ユーザー体験もアプリ利用者が理解しやすい。

## 4. 認可の設計（案 B の詳細）

### 4.1 データモデル（Pi 上 `authz.json`、git 管理外）

```json
{
  "enabled": true,
  "users": {
    "alice": {
      "enabled": true,
      "pubkey": "<Ed25519 公開鍵 base64 32B>",
      "history_tag": "MQTT:alice",
      "grants": [
        { "locks": ["sesame5_t", "sesame5_b"], "actions": ["lock", "unlock"] }
      ]
    },
    "cleaner": {
      "enabled": true,
      "pubkey": "<…>",
      "history_tag": "MQTT:cleaner",
      "grants": [
        { "locks": ["sesame5_b"], "actions": ["unlock", "lock"],
          "valid_from": "2026-10-01T00:00:00+09:00", "valid_until": "2026-12-31T23:59:59+09:00",
          "schedule": { "days": ["Tue", "Fri"], "hours": ["09:00-12:00"] } }
      ]
    }
  },
  "limits": { "unlock_per_minute": 3, "unlock_per_hour": 20 },
  "clock_skew_sec": 60
}
```

- **ユーザー** = 人（または端末）。鍵ペアは端末側で生成し、公開鍵だけを Pi に登録する。Pi に秘密は増えない。
- **grant** = 「どの錠に、どの操作を、いつ」。複数持てる。`lock` は安全側の操作なので広く、`unlock` は狭く与える運用を想定。
- `history_tag` は Sesame に送る履歴タグ（最大 21 バイト）。公式アプリの履歴に「MQTT:alice が解錠」と残る。
- 全体の `enabled: false` で遠隔操作を一括停止できる（キルスイッチ）。

### 4.2 判定順序（ブリッジ側）

1. 全体 `enabled` が true か
2. 署名が有効か（§5.3）→ 送信者が特定できる
3. ユーザーが存在し `enabled` か
4. `ts` が現在時刻 ± `clock_skew_sec` 以内か、`nonce` が未使用か
5. いずれかの grant が「錠 ∈ locks ∧ 操作 ∈ actions ∧ 期間内 ∧ 時間帯内」を満たすか
6. レート制限内か
7. 対象錠が BLE 接続済み・ログイン済みか

どれかで失敗したら実行せず、理由コードを結果トピックに返し、監査ログに残す。

### 4.3 失効と変更

- ユーザー失効: `enabled: false` にする、または削除。ブリッジは `authz.json` の更新を監視して即時反映する（再起動不要）。
- 端末紛失: そのユーザーの公開鍵を差し替える（新しい端末で鍵ペアを再生成）。
- 期限付きゲスト: `valid_until` が過ぎれば自動的に無効。

### 4.4 ユーザー鍵の配布（登録フロー）

1. アプリ側で Ed25519 鍵ペアを生成し、秘密鍵は端末のセキュア領域（iOS Keychain / Android Keystore）に保存する。秘密鍵は端末から出さない。
2. アプリが公開鍵を QR で表示する。
3. 管理者が Pi 側の管理ツール（`authz_admin.py add alice <pubkey>`）で登録し、grant を設定する。
4. 以後、アプリは秘密鍵でコマンドに署名する。

秘密鍵を配らないので、Sesame の secret 配布のような「QR を撮られたら終わり」にはならない。

## 5. プロトコル

### 5.1 トピック

| トピック | 方向 | retained | 内容 |
|---|---|---|---|
| `<p>/<alias>/cmd` | アプリ → Pi | × | 署名付きコマンド（QoS 1） |
| `<p>/<alias>/cmd/result/<req_id>` | Pi → アプリ | × | 実行結果（QoS 1） |
| `<p>/<alias>/event` | Pi → 全員 | × | 既存のイベントに `by: "alice"` を追加 |
| `<p>/bridge/authz` | Pi → 全員 | ○ | 遠隔操作の有効/無効と登録ユーザー数（秘密を含まない） |

### 5.2 コマンド payload

```json
{
  "v": 1,
  "req_id": "f3a9c1…",            // アプリ生成の一意 ID（結果の突き合わせと冪等性）
  "user": "alice",
  "lock": "sesame5_t",             // トピックの alias と一致しなければ拒否
  "action": "unlock",              // lock | unlock
  "ts": 1759810000,                // Unix 秒
  "nonce": "8e4b3f7c1a2b",         // 96bit ランダム
  "sig": "<Ed25519 署名 base64>"
}
```

### 5.3 署名と再送防止

- 署名対象: `sig` を除いたフィールドを**キー順に並べた JSON**（空白なし）の UTF-8 バイト列。
- 方式: Ed25519（アプリ側は tweetnacl 等、Pi 側は PyNaCl または `cryptography`）。共有秘密方式（HMAC）より、Pi に秘密を置かずに済み、端末ごとの失効が簡単。
- 再送防止: `ts` が窓外なら拒否。`nonce` は直近 24 時間分を Pi に保存（SQLite）し、重複なら拒否。`req_id` が重複なら前回の結果を返して再実行しない。

### 5.4 結果 payload

```json
{ "req_id": "f3a9c1…", "ok": true, "action": "unlock", "lock": "sesame5_t",
  "state_before": "LOCKED", "state_after": "UNLOCKED", "ts": "2026-10-07T04:33:21+00:00" }
```

失敗時: `{"ok": false, "code": "FORBIDDEN|BAD_SIG|REPLAY|EXPIRED|RATE_LIMIT|BLE_OFFLINE|TIMEOUT|DISABLED", "message": "…"}`

実行後、Sesame から mechStatus が届いて `state` が変わったことを確認してから `ok: true` を返す（最大 8 秒待つ。届かなければ `TIMEOUT`、ただしコマンドは送信済みの旨を含める）。

## 6. 安全装置

- **レート制限**: ユーザー単位と錠単位の両方（既定: 解錠 3 回/分、20 回/時）。
- **解錠の確認**: 解錠は BLE ログイン済みの錠にのみ送る。送信後に状態変化を確認する。
- **監査ログ**: 全コマンドを Pi の `audit.log`（JSON Lines）に残す。成功・失敗・理由・ユーザー・錠・req_id・送信元 client（ブローカーが提供すれば）。
- **通知**: 解錠イベントは全購読者に流れる（`event.by`）。将来のプッシュ通知に接続する。
- **キルスイッチ**: `authz.json` の `enabled: false`、または Pi 上で `authz_admin.py disable`。
- **フェイルクローズ**: `authz.json` が読めない・壊れている場合は全コマンド拒否。

## 7. ブローカー（多層防御の外側）

- 認証付きの無料枠（HiveMQ Cloud Serverless / EMQX Cloud Serverless）へ移行する。公開ブローカーでは遠隔操作を**有効化しない**（ブリッジは `mqtt.username` が空なら `cmd` を購読しない）。
- 認証情報はブリッジ用とアプリ用で分ける。可能なら ACL で、アプリ用は `cmd` への publish と `status/event/result` の subscribe だけ、ブリッジ用はその逆に限定する。
- 署名検証が本丸なので、ACL はあくまで追加の壁。ACL が無い無料枠でも安全性は §4〜§5 で担保される。

## 8. アプリ側の要件

- 鍵ペア生成と安全な保管（Keychain / Keystore）。公開鍵の QR 表示。
- 署名付きコマンドの生成（canonical JSON）。時刻同期（端末時計が ±60 秒以上ずれていれば警告）。
- 結果トピックを購読してから publish する（結果の取りこぼし防止）。
- 解錠は長押しや確認ダイアログなど、誤タップしにくい UI。

### 8.1 参照実装（Web アプリ）

`web/index.html`（mqtt.js + tweetnacl）。鍵は localStorage、署名対象は `authz.canonical_bytes` と同じキー順の compact JSON。詳細は `web/README.md`。

## 10. 実装メモ（2026-10-07）

| ファイル | 役割 |
|---|---|
| `pi/authz.py` | 権限表の読込（更新検知・フェイルクローズ）、Ed25519 署名検証、nonce（SQLite）、grant 判定、レート制限 |
| `pi/remote_control.py` | `cmd` 購読、認可 → ブリッジの BLE セッションで実行、結果返却、監査ログ、`--simulate` 用の偽装リンク |
| `pi/sesame_mqtt_bridge.py` | 上記を組み込み。`event.by` の付与、`bridge/authz` の publish、再接続時の再購読 |
| `pi/authz_admin.py` | 権限表の管理 CLI（init / gen-key / add / grant / revoke / enable / disable / allow / list） |
| `pi/remote_cmd.py` | Mac 用の署名付きコマンド送信クライアント（アプリ実装の参照実装） |
| `pi/tests/test_authz.py` | 認可ロジックの単体テスト 20 件 |
| `pi/authz.example.json` | 権限表の雛形 |

設計からの補足・決定事項:

- **署名方式は Ed25519**（pycryptodome の `Crypto.Signature.eddsa`）。公開鍵は raw 32 バイトを base64 で `authz.json` に置く。pycryptodome は raw 公開鍵を直接 import できないため、SPKI(DER) ヘッダを付けて読み込む。
- **フェーズ制御は `allowed_actions`**（全体設定）で行う。初期値は `["lock"]`。解錠を開放するときは `authz_admin.py allow lock,unlock`。
- **有効化条件**は `authz.json` が存在し、かつ `mqtt.username` が設定されていること。公開ブローカーでは `cmd` を購読せず、`bridge/authz` に `disabled: 公開ブローカー…` と出す。`--simulate` のときだけ例外的に有効（本番と分離するため接頭辞 `/sim`、クライアント ID `-sim` を自動付与）。
- 未知の錠（`devices[]` にない alias）宛の `cmd` は購読していないので結果は返らない。アプリは `devices` の一覧を `status` トピックから得ること。
- 同一 `req_id` の再送には前回の結果を返す（10 分保持）。nonce の重複は `REPLAY`。
- 施錠・解錠の完了判定は mechStatus の確定状態。応答 res=0 でも状態が確認できなければ `TIMEOUT`（コマンド送信済みの旨を含む）。
- ブリッジは Pi の唯一の BLE 接続を保持するため、コマンドは必ずブリッジ内の `LiveLink` から送る（§0 の制約）。
